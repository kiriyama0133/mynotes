这篇概述使用了cum 11-768课程里讲的内容，给出了智能体的经典定义和行动循环，再讨论一个真正好用的智能体需要哪些能力，以及训练语言模型与搭建harness两条路径各自解决了什么问题。

整体顺序是先看智能体能做什么，在哪里失控，再拆开它的行动循环，列出会决定成败的能力，回答这些能力该靠模型训练还是该靠harness工程补上，最后落到一个智能体系统的组成与课程的训练安排。

## 工具

Neubig将工具定义为： 语音模型用来调用的一个外部计算机程序的接口，调用工具有两类好处，源自于他与学生合著的综述《What Are Tools Anyway?》：

扩展，让模型做它根本做不到的事。例如，模型的知识是冻结的，无法知道“四个月前的今天是什么信息”，必须调用搜索工具来获取新信息。

辅助，模型本来能做，但用工具更省事、更可靠。例如，让模型心算两个七位数的乘法既慢又容易出错，而调用计算器可以瞬间得到精确结果。

同时，当工具的收益超过了延迟、成本、失败率和风险的时候，才应该去调用它，工具并非越多越好，越勤越好。

Neubig将工具调用这个能力拆分为了5个关联层次：

能力，模型具备哪些能力才能使用工具，例如理解工具的描述、生成符合语法的调用参数等。
机制：工具调用在底层是如何发生的，本质上，它只是模型吐出的一串特殊格式的token，harness负责解析这些token，执行对应的工具，并用call id 将结果与最初的调用请求关联起来，
约束：我们要保证模型生成的调用是合法的，可执行的，课程里也重点讨论了受限解码技术，它能强制模型输出符合特定格式比如json schema的token，同时也有一个局限，受限解码只能保证格式正确。不保证语义正确，比如说参数值是否合理。
接口：工具以何种形式暴露给模型，课程里对比了传统的REST API和现在流行的MCP，MCP的核心价值是充当凭证中介，更安全地管理工具调用所需授权，同一个模型在不同provider的部署下，工具调用的错误率可能差别很大，这个凸显了接口实现的重要性。
系统：将工具调用放在更大的agent系统里考量，涉及如何管理并行调用、处理调用失败、进行结果校验等工程问题。

我们可以用deepseek harness和输出工具调用的一系列特殊token来演示，目前已知的主要格式包括：

- **原生特殊 Token 格式**：这是最典型的一种，结构类似于 `<｜tool▁call▁begin｜>function<｜tool▁sep｜>NAME<｜tool▁sep｜>{...}<｜tool▁call▁end｜>`。一个具体的例子是 `<｜tool call begin｜>function=bash<｜tool sep｜>{"command": "pytest"}<｜tool call end｜>`。请注意，这些标记中的竖线通常是**全角竖线（`｜`，U+FF5C）**，而非 ASCII 的 `|`，这是 DeepSeek 标记语法的一个细节。

在deepseek v3.2 v4之中工具调用可能采用一种接近XML语法的DSML封装，DSML叫做 deekseep markup language，很直接，其外层包裹可能是`<｜DSML｜function_calls>` 或 `<｜DSML｜tool_calls>`，内部则使用 `<｜DSML｜tool name=...>` 和 `<｜DSML｜parameter name=...>` 来定义工具名和参数。

在标准的、支持原生工具调用的 API 调用中，这些原始标记**正常情况下应由模型编码进 OpenAI 兼容的结构化 `tool_calls` 字段**，而不是直接混在 `content` 文本里泄漏出来。Harness 的角色，就是解析模型输出的这些标记（或结构化的 `tool_calls` 字段），并将其转换为内部统一的工具调用指令。

deepseek harness在设计上同时支持原生工具和mcp工具，harness本身定义了一套工具注册和调用机制，开发者可以用`defineTool` 创建工具，并用 `ctx.tools.register()` 将其注册到工具服务中。这些工具直接由 Harness 管理，其调用过程依赖于上述的特殊 token 或结构化的 `tool_calls` 字段，**不需要**经过 MCP 协议。

mcp才是扩展外部工具的标准接口，为了接入外部生态工具，deepseek官方提供了`@deepseek-ai/dsh-mcp-client` 这个客户端包，能够让模型能够像调用原生工具一样，去调用外部mcp服务器上提供的工具，通过这个客户端接入的工具，在模型看来其名称会带有 `mcp__<serverName>__<tool>` 这样的前缀，以作区分。

## 系统提示词组装

上面讲了工具调用和接口问题，那么我们现在重点是让模型能够输出我们想要的特殊格式token，要让模型输出特殊格式的 Token 并转化为工具调用，关键不在于某一次性的“魔法提示词”，而在于 DeepSeek Harness 在**两个层面、不同阶段**的协同注入：**系统提示词的静态组装**与**运行时的动态引导**。

harness并非把写死的提示词给模型，而是在每个模型步骤开始的时候动态组装一份有序系统提示词，系统提示词会包含一个特定的协议提示词段，它明确告知模型：“你可以通过书写 `<｜DSML｜function_calls>` 这样的块来调用函数”，并给出具体的语法范例。这个规约的拼接顺序通常是固定的，夹在客户端 system 消息和工具声明之间，确保模型能稳定地“看到”输出格式的要求。

但是仅仅知道模型还不够，模型还需要知道哪些工具可用，参数是什么，Harness 的流程是：**先注册工具**，然后**将工具的 Schema 注入系统提示词**，使模型能够看见它们。在系统提示词的有序 section 中，工具指引通常占据专门的区间（例如序号 `1000–3100`）。因此，工具调用的“格式规约”和“可用工具定义”是在系统提示词组装阶段一起注入的。

然后是运行时的动态注入，系统提示词设定了什么可以做，什么怎么说，但是模型何时决定行动还收到了运行时上下文的引导，harness提供了在轮次中间、每个步骤注入提示词的限制，以 `dsh-prompt-inject` 这类插件为例，它不改动系统提示词，而是通过 `agent/pre-step` 钩子注入**用户消息**。这种注入可以按条件触发。

## 上下文管理

如果每一次工具调用和结果都塞回历史的话，那么智能体的上下文就会疯涨，因此上下文是结构性问题，而非工程意外。

>对 OpenHands 1500 个真实会话的统计进一步印证了这一点：平均每个会话消耗 **77,922 token**，其中**工具结果占 37%**，系统提示与工具描述占 23%，而用户消息仅占 9%。这意味着，**即便用户只说了一句话，智能体的上下文也可能已经非常“胖”了**，大头全是工具交互的副产物。

因此这个课程的第三节课讲了怎么让模型能有更长的上下文，他讲解决方案拆解为了模型层和harness层两条线，共同服务于**增长 → 推理瓶颈 → 架构选择 → 缓存复用 → 压缩兜底**。

架构上，主流做法是混合注意力，大部分层只做局部计算，隔几层插入一次全局注意力，负责取回之前的信息。课程介绍了四类具体机制——**滑动窗口注意力、线性注意力/循环模型、稀疏注意力、KV 压缩**——它们本质上都是在给“每次需要比较的 token 数量”设上限，把标准注意力的 **O(n²)** 成本降为 **O(wn) 或 O(n)**。

仅有架构不够，模型还必须在训练中真正“见过”长文本。课程介绍了**长度课程**的思路：先以 4K–8K 的短序列打基础，再逐步拉长到 32K–128K，最终到 1M。位置编码（如 RoPE 及其外推变体 YaRN）在这里扮演关键角色，帮助模型处理训练时未曾见过的超长距离。

agent开发者要注意的部分是缓存复用问题，缓存复用是如果Prompt的前缀保持不变，其对应的KV状态就不必重新计算，缓存命中的 token 成本可比普通输入**低约十倍**，**90%–95%** 的命中率是一个良好的工程目标。

![](https://pub-dd8e151a60af44cfbe36beaaf0ad54e8.r2.dev/2026/11/1795592477557-9if68npd.webp)

蓝色部分是缓存的输入，可以直接复用，无需重新计算。红色是新输入的token需要进行prefill预填充计算，黑色是模型生成的输出token，灰色是外部工具返回的结果。

上一步的所有内容（红+黑+灰）现在都变成了 🟦 **蓝色（已缓存）**。整个前缀可以直接复用，极大地节省了计算时间和成本。

call3里，前两轮的所有交互变成了蓝色缓存，结果就是“The reusable prefix keeps growing”（可复用的前缀不断增长）。这就是 Agent 运行越久，上下文越长，单次请求的缓存命中量越大的原因。 滚雪球效应。

如果上下文逼近了上限，那么我们就该进行压缩，第三讲将压缩提升到了一个更严谨的层面。本质上是一个状态估计问题，必须满足行为保真，有界、可恢复性三条约束。个压缩后的历史，必须能让模型在其中执行任务。而不是仅仅看起来更短。因此，评估压缩质量必须用 **“继续式评估”**，看模型在压缩后的历史上能否继续完成任务，而非只看省了多少 token。

在工程上处理就有个核心矛盾，压缩必然破坏提示缓存，工程实践的目标不是不压缩而是尽可能少压缩，尽可能晚破坏缓存， MAF的设计也是这样的。

提示缓存匹配的是精确前缀，只要开头的一段字节完全一致，服务端就可以复用之前计算好的KV状态，大幅降低成本，但压缩的本质是重写历史，一旦你改动了历史的其中一段，这段改动的整个前缀就变了，缓存就会失效。`maf-compaction` 包的开篇就点明了这个事实：**“every compaction rewrites history inside that prefix, so compaction breaks the cache by construction”**。所以，任何压缩策略都必须正视这个代价。

maf的agent harness已经内置了自动上下文压缩，它会在工具调用链进行到中途的时候监控token用量，一旦接近了上下文窗口上限，就会自动压缩聊天历史，防止溢出，过 `AsHarnessAgent` 配置好 `MaxContextWindowTokens` 等参数，它就会在后台运行。同时，MAF 本身**停留在 Provider 中立的消息编排层**，它负责编排消息，但缓存能否命中，最终取决于发送给具体 Provider 的请求是否保持了稳定的前缀。

## agent的记忆和技能

第三讲；留下了一个问题，一次任务结束之后，agent学到的东西，是否也必须跟随上下文一起被清空？

本质是在探讨agent不应该每次都从0开始：

讲座以一个购物网站 Agent 开场：“把 Sony 耳机加入愿望清单”和“查无线键盘的价格范围”是两个不同的任务，但它们的前半段几乎一样：进入商店 → 找到搜索框 → 输入关键词 → 点击搜索。如果 Agent 第一次花了很多步才搞清楚这个网站的搜索框怎么用，第二次理应直接复用这段经验。**Skill 的基本动机，就是把一段经验证有效的行为，抽象成可再次调用的知识**，而不是每次都重新探索。

Fried 首先把“让 Agent 变得更好”拆解为三个可以存储经验的地方，第四讲聚焦的是中间那个：

|位置|优势|劣势|
|---|---|---|
|**Context（上下文）**|对刚刚发生的事保真度最高|昂贵、嘈杂，且无法跨任务持久化|
|**External Artifacts（外部制品）**|**可审查、可编辑、可检索、可移植**|需要被归纳、选择和持续维护|
|**Model Weights（模型权重）**|速度快，能带来广泛的行为改变|更新慢、不透明，且绑定特定模型|
外部制品的优势是可移植，一份“如何在这个网站搜索商品”的描述，对任何模型都有效；而一次权重更新，只对那一个模型有效。它还有一个“免费的”人机协作接口：**Agent 提出，人来编辑**。

讲座里将跨任务经验分为了三个层级，粒度的选择决定了存什么：
episode，完整经历，每一次观察和动作的原始序列。保真度最高，但最冗长、最难复用。
fact，这个商店的价格只在商品详情页显示。”当这个事实会反复出现，或需要被更新时，值得存储。
skill，填充搜索框 → 点击搜索 → 打开结果。”当后续任务会重复同一个**行为模式**时，它是最有价值的抽象。

在圈外人里看来，应该影响最大的是skill，人类可以直接编写skill，载体通常是个SKILL.md文件，配合scripts、references、assets等资源，关键机制是**Progressive Disclosure**，系统不会把完整的 Skill 内容一次性塞进上下文，而是按 **Trigger（触发）→ Load（加载）→ Execute（执行）** 的节奏，只在需要时才逐步展开细节。效果是显著的：在 **SkillsBench** 基准上，引入人类编写的 Skill 后，平均通过率从 **33.9% 提升到了 50.5%**。

其二，skills让模型知道了怎么做，memory回答了应该记住什么，讲座里回顾了几种代表性的外部记忆机制：

- **MemGPT**：借鉴操作系统的分层存储思想，把上下文当作“快内存”，外部存储当作“慢内存”来管理。[文档](https://blog.csdn.net/naRuTo1325/article/details/166139146#1)
- **Mem0**：强调记忆不是只追加，而是有 **Add / Update / Delete / No-op** 四种操作，需要决定何时遗忘或更新。[文档](https://blog.csdn.net/naRuTo1325/article/details/166139146#1)
- **Reflexion**：保存的是**语言化的失败反馈**（“错在哪里”），而不仅仅是成功轨迹。

并且模型是可以自己从成功或者失败的轨迹里归纳出可复用的skill的，一个典型流水线是：**Episode → Judge（评判）→ Induce（归纳）→ Admit（准入）**，即先判断哪些经历值得学习，再从中提取模式，最后决定是否将其纳入技能库，越用越聪明说是，虽然这个框架上是成立的，SAGE等框架实现了过，在 AppWorld 基准上实现了 **8.9% 更高的目标完成率，同时交互步数减少 26%、token 生成量减少 59%**。这说明“自我进化”在受控实验中是有效的。

>但工业视角下的现实要冷峻得多。一项覆盖多个系统的评测给出了一个刺眼的数据：**人类 curated 的 Skill 相比无 Skill 基线提升 +16.2 个百分点，而 LLM 自行生成的 Skill 提升为 +0.0 个百分点**。也就是说，**“能自己写 Skill”和“写出来的 Skill 有用”之间，存在一道巨大的鸿沟**。自动生成的 Skill 往往粗糙、不可靠，真正好用的仍然依赖人工打磨。

现在skill的影响太大了，开源技能库的体量就印证了大量开放的说法，一个聚合项目声称集了 **90,000+ 个通用 Agent Skill**，来源包括 ClawHub（69,842 个）等注册中心。另一个爬取项目从 842 个 GitHub 仓库中提取了 **11,389 个 Skill**，93% 完成了领域分类。

西门子的工业 Agent 通过专用 Skill 查询和控制楼宇设备，支持跨系统联动与健康巡检，图纸 BOM 错误率控制在 **1% 以下**。炼油规划软件中也出现了面向 AspenTech PIMS 这类专业系统的技能归纳与执行验证工作。

但是episode和fact为啥没有，有点怪。eposiode保真度虽然高，但是很贵，太嘈杂，无法跨任务直接复用，fact是离散的知识点，单独使用优先，skill才是真正的可执行的行动知识。
