## 数据库的锁

之前有一个问题，pg修改一个表里的一个数据的一个字段，lock的是这个数据还是这个数据，还是说实现的更加复杂。在经过了查找之后，我发现，**在 PostgreSQL 中，默认情况下，修改某一行的一个字段，锁住的就是“这一行数据”（Row-Level Lock），而不是整张表。**

当你执行 `UPDATE users SET name = '张三' WHERE id = 1;` 时，其他用户完全可以同时更新id = 2的行，或者插入新的数据，不会对表上锁。pg在底层给id = 1的这一行会添加一个叫做排他锁，如果此时有另一个事务视图去更新id = 1的记录，他就会被阻塞挂起，直到上一个事物提交或者回滚。

这里只介绍基本的对数据库强相关的锁机制，除此以外还有共享锁、悲观锁、乐观锁、行锁、表锁。

传统数据比如说mysql的innoDB，是在航头加标记，或者用链表把锁穿起来。pg是：你修改一个字段，实际上就是在复制这一行，执行 `UPDATE` 时，PG **不会**去修改原来的那条物理数据（老版本）。老版本依然保留在磁盘上（用于给其他正在读取的事务看，这叫 MVCC 多版本并发）。PG会在表里插入一条全新的物理行，带上新数据，以及系统隐藏字段xmin事务ID，然后PG在新插入的这一行的头部xmax字段加上锁标记。最后pg把旧的那条物理行标记为已死，（实际上就是打个标记，等 `VACUUM` 进程来清理）。

mvcc的特点在于 读永远不阻塞写，写永远不阻塞读，当有事务在`UPDATE` 这一行时（正在生成新版本，但还没提交），它会给新版本打个标记（`xmin` 是当前事务 ID）。另一个事务来 `SELECT` 这一行，PG 会检查：这个新版本的事务 ID 还没提交，**对我不可见**。

mvcc机制和传统数据库比如SQL Server或者MySQL的innoDB的核心区别之一就是，PG中，单纯的读操作永远不会阻塞写操作，写操作不会阻塞单纯的读操作，因此我们使用Entity Frame Core中，默认生成的查询SQL绝对不会有任何锁语法，比如说FOR SHARE或者FOR UPDATE。linq设计哲学是面向普通业务查询的，ef core默认使用数据库的read committed隔离级别，配合pg的mvcc机制，普通的SELECT语句就是直接去读快照，根本不需要也不会在SQL层面加上FOR SHARE这种显示的行级共享锁。

你写：

```cs
var user = await _dbContext.Users.FirstOrDefaultAsync(u => u.Id == 1);
```

EF Core 生成的 SQL 就是纯粹的：

```sql
SELECT * FROM users WHERE id = 1 LIMIT 1;
```

虽然默认不生成，但在高并发场景下（比如：读取账户余额判断是否足够，然后扣款），你可能确实需要加锁。在 EF Core 中，你**必须手动（显式）** 附加锁指令。你想一下一个场景，用户余额是100元，然后突然来了两个请求，事务A、事务B，都要扣100。

**A** 执行普通 `SELECT`，利用 MVCC 读到快照：余额 100。判断足够，准备扣款。
B 紧接着执行普通 `SELECT`，因为此时事务 A 还没提交，MVCC 依然给了它旧快照：余额 100。判断也足够，准备扣款。**A** 执行 `UPDATE`，把余额减 100 变为 0，**提交**。**B** 醒来执行 `UPDATE`，把余额减 100 变为 -100，**提交**。

这个叫做**丢失更新**。但是普通的SELECT读到快照不是坏事，而是常态，因为pg中，如果读操作不需要修改数据，读到旧数据是没有问题的，这也是mvcc极大提升读性能的根本原因，但关键是，这里的先读后写的原子性被破坏了，.net代码里`SELECT` 和 `UPDATE` 是两条独立的 SQL，这中间有微小的时间差，给了其他事务可以插队的机会。

所以我们会使用悲观锁来解决这个问题。

### 悲观锁解决并发不高的场景

悲观锁是假设坏的情况发生，当一个事务 A 读取数据时，直接给这一行加个“排他锁（X锁）”。如果事务 B 也想读或写，那就不行，数据库直接让 B 挂起（排队等待），直到 A 提交或回滚，B 才能继续。

这个是绝对安全的，数据具有强一致性，只要有锁在，别人就没有插队读取、修改。但是并发的性能很差，如果事务A执行了5s，这5s内的所有想操作这行数据的请求就会全部阻塞，容易引起吞吐量下降、死锁。

### 乐观锁解决高并发场景

这个和上面的悲观锁不一样，假设的是别人不会那么巧跟我同时改，所以我不锁，但在最后提交的时候，我得检查一下有没有人偷偷改过。

在ef core中，我们经典的是加一个version版本号或者rowversion时间戳字段，读取数据时，不加任何锁，把数据和版本号一起读到内存里。更新数据时，带上条件：

```sql
UPDATE users SET balance = balance - 100, version = version + 1 WHERE id = 1 AND version = 5
```

如果数据库返回的影响行数是 `0`，说明刚才有人偷偷改过（版本号变了），你的更新失败了。此时你的代码捕获异常，重试（重新读取、重新计算、重新更新）。

这个没有任何锁等待，因此数据库并发性能极高，如果并发冲突极高，比如说1w的请求直接同时过来，就会有大量请求更新失败重试，cpu直接占用飙升。

在 .NET 里，配置乐观锁非常简单。你只需要在实体上加一个 `[Timestamp] public byte[] RowVersion { get; set; }`，EF Core 会在底层自动把 `WHERE RowVersion = xxx` 加上，如果抛出 `DbUpdateConcurrencyException`，你在中间件里统一捕获，给前端弹一个“数据已被他人修改，请刷新重试”即可。

### 读写分离的场景下锁怎么用

锁的机制和底层数据库原因下，这个本身没有任何区别，不管是ef core还是dapper，这个叫做CQRS 命令查询职责分离，最终发给pg的都是一样的sql语句，因为这个是为了代码解耦和查询性能优化。

只是说读写分离的架构上，怎么用锁，哪个库上用锁，有很大区别，因为你在主从模式下，读和写的库是不一样的数据库，两个库使用完全一样的全量数据模型，写操作去主库，读操作去的是从库，主库写完之后会在几毫秒内同步给从库。这个模型在突发流量等场景下有很大作用，如果几万个请求进来，数据库的读和写就会达到极限，如果用了主从分离，整体的抗压能力就会有成倍的提升。

写入库承担`UPDATE`、`DELETE`、`INSERT`。读库承担`SELECT`。pg的主从同步是异步的，意味着，当你在主库里提交了扣款，数据库立刻返回成功，但数据复制到从库可能有 10~50 毫秒的延迟。

如果用户扣款成功，前端立即发起查询，这个请求被dapper路由到了从库，从库没有同步完，返回了旧库，返回了旧数据。我们普遍就将写操作之后的立即读取强制走主库。

在我们的Genocs的DDD架构项目里来说，CQRS已经完成的差不多了，CQRS天然就和主从分离非常的契合。我们在appsetting.json里也就是定义读和写两个配置。在写侧：注册 `Web3dContext` 时，读取 `MasterDb`。从侧：写一个 Dapper 的连接工厂，强制读取 `ReplicaDb`。

### 排他锁

排他锁是pg里最严格的锁，这个锁是加在行上的，当你对一行数据加上X锁之后，会挡死其他事务的UPDATE、DELETE，**想用 `SELECT ... FOR UPDATE` 或 `FOR SHARE` 查这行**：阻塞。

但是通过刚才的mvcc机制我们知道，排他锁不会阻塞普通的`SELECT` 查询。因为普通 `SELECT` 走的是 MVCC 快照。你加 X 锁修改了数据（生成了新版本），普通 `SELECT` 查不到你未提交的新版本，它会去读那个旧的物理版本。所以，**写（加 X 锁）和普通读，在 PG 里依然是互不干扰的。**

到这里，MVCC、主从分离、S 锁、X 锁、乐观/悲观锁，这一条从数据库底层到应用架构的完整知识链路就有了。

Outbox的核心步骤里，X锁也是参与进来了的，比如一个场景：你要扣减库存和发送通知，发送通知算是outbox事件的本地事务，排他锁会隐式介入：

```sql
BEGIN;

-- 1. 更新业务表（PG 底层自动给这行加 X 锁，防并发扣减超卖）
UPDATE Inventory SET stock = stock - 1 WHERE id = 100;

-- 2. 写入 Outbox 表（插入新行，不涉及原有行的锁冲突）
INSERT INTO outbox_messages (event_type, payload) VALUES ('StockDeducted', '{...}');

COMMIT; -- 事务提交，X 锁释放
```

**在这里，X 锁的作用是：** 确保 `UPDATE` 那一步是线程安全的，防止两个请求同时把库存改成负数。**但它并不能替代 Outbox 的作用**，就算没有 Outbox，更新库存依然会有 X 锁。Outbox的机制最巧妙的是worker把消息安全地拿过来消费，如果 3 个 Worker 同时去扫 `outbox_messages` 表，怎么保证同一条消息不被发 3 次？

这就是我们上一轮讲的 **`FOR UPDATE SKIP LOCKED`**：

```sql
SELECT * FROM outbox_messages 
WHERE status = 'Pending' 
LIMIT 10 
FOR UPDATE SKIP LOCKED;
```

worker A用FOR UPDATE用X锁锁住前10条消息，B来扫的时候发现前10条被锁，它会**直接跳过**（`SKIP LOCKED`），去锁第 11-20 条，这仅仅是 PostgreSQL 提供的一种极其高效的**任务分发机制**。
